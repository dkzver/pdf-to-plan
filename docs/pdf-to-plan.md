# PDF-чертёж → планировка: как это делается

Документ описывает рабочую схему и то, что уже собрано в `tools/pdfplan/`. Прототип проверен на синтетическом чертеже: векторный путь — 7 из 7 стен, растровый — 7 из 7, ошибка осевой 0,1 pt.

## 1. Конвейер

```
PDF
 ├─ 1. Классификация страницы: вектор / растр / смешанная
 ├─ 2. Вектор: операторы рисования → стены, проёмы
 │    Растр: 300 dpi → бинаризация → скелет → расстояние → отрезки
 ├─ 3. Склейка: коллинеарные, двойные линии, вставки, узлы, дубли
 ├─ 4. Схема: стены (осевые + толщина), проёмы, узлы, комнаты
 ├─ 5. Правка человеком: концы, толщина, лишнее/пропущенное
 └─ 6. Экспорт: JSON → редактор планировки
```

Ключевое решение: **не пытаться сразу получить «красивый план»**. Сначала геометрия (стены + толщина), потом семантика (комнаты, двери, окна), потом отделка. Ошибки на каждом шаге видны и правятся отдельно.

## 2. Классификация: вектор или растр

Признаки страницы (PyMuPDF):

| признак | что значит |
| --- | --- |
| `len(page.get_drawings())` | число векторных путей. ≥ 8 — есть настоящая геометрия |
| площадь картинок / площадь страницы | ≥ 0,6 — страница фактически картинка (скан) |
| текстовый слой | есть — скорее экспорт из CAD; нет — скан |

Правила прототипа: `vector` при ≥ 8 путях и площади картинок < 0,6; `raster` при одной большой картинке и < 8 путях; иначе `mixed` — сначала пробуем вектор, при пустом результате падаем в растр.

Важно: PDF может быть «векторным» формально, но содержать растр, вставленный в векторную страницу (так делают многие сканеры). Поэтому решает не формат файла, а содержимое страницы.

## 3. Векторный разбор

`page.get_drawings()` возвращает пути: `('l', p1, p2)` — линия, `('re', rect)` — прямоугольник, `('c', …)` — кривая, плюс `width`, `fill`, `type` (`s` — обводка, `f` — заливка, `fs` — обе).

Что считается стеной:

1. **Залитый прямоугольник** с отношением сторон ≥ 3 и толщиной 2–45 pt → осевая по длинной стороне, толщина = короткая сторона. Это самый частый вид стен в CAD-экспорте.
2. **Толстая линия** (width ≥ 2 pt, длина ≥ 20 pt) → осевая = сама линия, толщина = width.
3. **Две параллельные тонкие линии** на расстоянии 6–34 pt с сопоставимой длиной и перекрытием ≥ 65% → одна стена по центру, толщина = расстояние. Так выглядят стены в архитектурных чертежах, где стены не залиты.

Что не считается стеной:

- одиночные тонкие линии (размерные линии, створки дверей, линии окон) — отбрасываются на последнем шаге по толщине < 2,2 pt;
- рамка листа и штамп — тонкие линии у краёв страницы;
- кривые (дуги открывания) — в стены не идут, но пригодятся для определения дверей.

**Проёмы.** Белая заливка поверх стены — это не стена, а «подчистка» проёма. Прототип собирает такие прямоугольники отдельно и классифицирует: если внутри 2+ тонкие линии — окно, иначе дверь. Это даёт проёмы почти бесплатно и без ML.

**Постобработка** (общая для обоих путей):

1. Склейка коллинеарных отрезков: угол ±2,5°, смещение ±3,5 pt, разрыв до 14 pt (стыки и проёмы).
2. Удаление вставок: тонкий короткий отрезок, лежащий на толстой стене, — окно или проём, не стена.
3. Сведение узлов: концы в радиусе 6 pt получают общие координаты, почти ортогональные стены выпрямляются (±2°).
4. Дедупликация: одна стена, обведённая контуром и залитая, даёт два отрезка — оставляем более толстый.

## 4. Растровый путь

1. Рендер страницы в 300 dpi (для A4 это ~3500×2500 px).
2. Порог Otsu, инверсия: чернила = 255.
3. Удаление мелких компонент (буквы, стрелки, точки) — площадь < 220 px.
4. Скелет (`cv2.ximgproc.thinning`) — линия толщиной 1 px по оси каждого штриха.
5. Карта расстояний (`distanceTransform`): в точке скелета значение ≈ половина толщины штриха.
6. `HoughLinesP` по скелету: отрезки, затем для каждого берётся медиана карты расстояний в средней части → толщина в pt.
7. Отсечение тонкого (< 2,2 pt) — размерные линии, окна, дуги.
8. Та же склейка, что и для вектора.

Почему не контуры и `minAreaRect`: у плана стены пересекаются, контуры слипаются в один объект, и прямоугольник описывает весь дом. Скелет + карта расстояний даёт ось и толщину каждой стены независимо от пересечений.

## 5. Масштаб и комнаты (следующий слой)

**Масштаб.** В pt чертёж не имеет метров. Варианты по возрастанию сложности:

1. Пользователь задаёт одну стену известной длины — деление даёт pt/мм. Это то, что делают Homestyler и RoomSketcher.
2. Читать размерные числа: текст на странице + ближайшая размерная линия → цепочка размеров → масштаб. Работает на CAD-экспорте, где текст настоящий.
3. Читать штамп «М 1:100» — самый дешёвый, но самый ненадёжный путь.

**Комнаты.** Осевые линии стен → `shapely.ops.polygonize` по замкнутым контурам (с допуском на замыкание) → площади. Комнаты, не замкнутые из-за проёмов, требуют «достройки»: продлить стены до пересечения в пределах толщины. Это отдельный шаг, который стоит делать после правки человеком, а не до неё.

**Двери и окна.** Проёмы из белых заливок (вектор) или разрывы в стене + дуга (растр). Дуга даёт сторону открывания: вектор — радиус и направление кривой, растр — окружность, вписанная в разрыв.

## 6. Продуктовая архитектура

| вариант | плюсы | минусы | когда выбирать |
| --- | --- | --- | --- |
| **Локальный CLI + просмотрщик** | приватность, нет сервера, быстро проверять гипотезы | нет совместной работы, установка Python | прототип, внутренний инструмент |
| **Desktop (Tauri/Electron + Python sidecar)** | файлы не покидают машину, доступ к ФС, большой PDF | две среды, обновления, вес | если чертежи клиентов конфиденциальны |
| **Web: FastAPI (Python) + Next.js** | один UI для правки, легко масштабировать, PDF разбирается на сервере | файл уходит на сервер, нужен воркер и очередь | SaaS, массовый пользователь |
| **Полностью в браузере (pdf.js + OpenCV.js)** | файл не покидает браузер, нет бэкенда | pdf.js даёт операторы, но не геометрию; CV в WASM медленный; тяжёлые PDF | если приватность — главный аргумент |

Рекомендация для этого проекта: **FastAPI + Next.js**, разбор в отдельном воркере (PDF до 50 МБ, 10 страниц), результат — JSON, который открывается в том же редакторе планировки, что и ручной план. Для конфиденциальных клиентов — тот же Python-код в desktop-сборке.

Схема сервиса:

```
POST /api/parse        multipart pdf, page  -> job_id
GET  /api/jobs/{id}    статус, прогресс
GET  /api/plans/{id}   plan.json (стены, проёмы, узлы)
POST /api/plans/{id}   правки пользователя (патч стен)
POST /api/export       pdf/png/svg/json
```

Разбор — идемпотентная задача: одинаковый файл + страница дают одинаковый результат, версия алгоритма хранится рядом с планом, чтобы правки не «съезжали» после обновления парсера.

## 7. UX правки

Минимум, без которого схема бесполезна:

- стены рисуются осевыми линиями с толщиной; видно, что нашлось, поверх исходного PDF;
- концы тянутся, прилипают к соседним узлам (10 px);
- удаление и добавление стены, отмена (Ctrl+Z);
- подсветка уверенности: найденное толстым — уверенно, тонкое и короткое — под вопросом;
- экспорт в формат редактора без потери координат.

В прототипе это `viewer.html`: автономный файл, внутри plan.json и картинка страницы. Проверено: перетаскивание конца меняет координаты в pt, добавление и удаление работают, отмена возвращает исходное состояние побайтово.

## 8. Точность и ограничения

| вход | что ожидать |
| --- | --- |
| векторный PDF из CAD (залитые стены) | 90–100% стен, толщина точная |
| векторный PDF с двойными линиями | 80–95%, зависит от проёмов и мебели |
| чистый скан 300 dpi, без поворота | 60–85%, обязательна правка |
| фото чертежа, наклон, тени | 30–60%, часто быстрее обвести заново |
| ручной эскиз | не автоматизируется, только подложка |

Ограничения прототипа, которые нужно закрыть в продукте: нет чтения размерных чисел и масштаба, нет комнат и дверных дуг, нет поворота/деп skew скана, нет многостраничности и многоэтажности, нет ML-резерва для грязных сканов.

## 9. Дорожная карта

| этап | что делается | срок |
| --- | --- | --- |
| 1. Прототип (сделано) | классификация, вектор, растр, склейка, JSON, просмотрщик | 2–3 дня |
| 2. Масштаб и комнаты | калибровка по стене, чтение размеров, polygonize, площади | 1 неделя |
| 3. Проёмы и двери | типы, сторона открывания, привязка к стене | 1 неделя |
| 4. Сервис | FastAPI, очередь, хранение, версия парсера, лимиты | 2 недели |
| 5. Редактор | канва с привязками, слои, отмена, экспорт в план | 3–4 недели |
| 6. Качество | тесты на 20–30 реальных чертежах, метрики, ML-резерв | постоянно |

MVP (этапы 1–4): 4–5 недель одним разработчиком. Продукт с редактором и приёмкой на реальных чертежах: около 3 месяцев.

## 10. Юридическое и приватность

- Разбирать только те чертежи, на которые у пользователя есть права; сервис должен это явно принимать в соглашении.
- Не хранить исходный PDF дольше задачи; результат — по выбору пользователя.
- Не выкладывать чужие планы в галерею без согласия.
- Для desktop-варианта обработка локальная — это аргумент продажи для архитекторов и риелторов.

## 11. Что уже лежит в репозитории

```
tools/pdfplan/
  fixtures.py        генератор тестовых чертежей (вектор + растр + эталон)
  pipeline.py        классификация, извлечение, склейка, SVG
  cli.py             python cli.py plan.pdf --out out/
  evaluate.py        precision/recall против эталона
  make_viewer.py     plan.json + страница -> автономный viewer.html
  viewer_template.html  просмотрщик с правкой концов, добавлением, отменой
  fixtures/          plan_vector.pdf, plan_raster.pdf, truth.json, результаты
```

Команды:

```bash
python tools/pdfplan/fixtures.py
python tools/pdfplan/cli.py tools/pdfplan/fixtures/plan_vector.pdf
python tools/pdfplan/evaluate.py tools/pdfplan/fixtures/truth.json \
       tools/pdfplan/fixtures/plan_vector_plan/plan.json
python tools/pdfplan/make_viewer.py tools/pdfplan/fixtures/plan_vector_plan
```

Результаты на фикстуре: вектор — precision 1.00, recall 1.00, ошибка толщины 0 pt; растр (200 dpi картинка) — precision 1.00, recall 1.00, ошибка толщины 0,1 pt, осевой 0,1 pt. Это верхняя граница: чертёж чистый и синтетический.
